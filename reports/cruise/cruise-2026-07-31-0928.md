## 4. 本轮实质产出：#39163 诊断（W32 第 8 份，超额）

**为什么选它：** 这是本轮唯一新增 issue，且落在 ARK 核心叙事的正中央——它是 **observability 组件自身的可靠性缺陷**。

**缺陷：** `trace_as_chain_group()` / `atrace_as_chain_group()` 只 `except Exception`，而 `asyncio.CancelledError` 与 `KeyboardInterrupt` 继承自 `BaseException`，因此任务取消同时绕过 `on_chain_error()` 与 `on_chain_end()`。已 start 的 run 永远拿不到终态事件，在 LangSmith 里无限 pending。

**ARK 实机离线复现 4/4（无 API key、无网络）：**
```
A  async  · asyncio.CancelledError   started=1 ended=0 errors=0   BUG: run left PENDING
B  async  · ValueError    (control)  started=1 ended=0 errors=1   OK (terminal fired)
C  sync   · KeyboardInterrupt        started=1 ended=0 errors=0   BUG: run left PENDING
D  sync   · ValueError    (control)  started=1 ended=0 errors=1   OK (terminal fired)
```
B/D 对照组证明回调管线本身完好，问题精确锁定在异常基类选择。验证于 langchain-core 1.5.3。

**产出物：**
- `scripts/repros/repro_39163_cancelled_leaves_run_pending.py`（第 6 份 repro，四例对照式）
- `docs/reports/ark-report-39163-20260731.html`（第 21 份诊断报告）
- `docs/reports/ark-defect-pattern-index.md` 升级 v2.7：F3 族 4→5 例

**族谱意义（本轮最有价值的发现）：** #39163 是 F3「静默失败」族的**新亚型**。前 4 例（#39039/#38892/#38893/#39099）都是「失败伪装成成功」——至少产生了一个错误的值，事后审计能在数据里找到矛盾。#39163 把 F3 推到极端：**连伪装都没有，终态事件根本不发生**。run 有 start 无 end 无 error，在任何遥测后端里都与「真实的长任务」不可区分。

这直接分化了 ARK 的防线设计：前四例靠 `OutputValidator` 校验**终态的内容**，本例必须靠 `Trace` 校验**终态的存在性**（span 退出无终态则自动补发 `ark.span.orphaned`）。

**三点使其成为索引中最强证据：**
1. 触发条件是生产常态而非边缘情况 — WebSocket 断连即 `CancelledError`，交互越重的服务遥测污染越严重
2. **同文件内已有正确写法** — `manager.py` 里 runnable 回调辅助函数已 catch `BaseException`，两个 chain group CM 仍写 `except Exception`。这不是设计取舍，是纪律漂移，是「靠人自觉」不可持续的直接物证
3. 它发生在 observability 组件自己身上 — 负责「记录一切」的模块自身缺终态不变式
