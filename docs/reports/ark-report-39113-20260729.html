问题摘要

🔴

用户用官方推荐的 create_text_block() 构造合成对话历史（压缩/摘要长对话的常见做法）时，工厂方法会给每个块铸造 lc_<uuid4> 形式的 id。 langchain_openai._construct_responses_api_input() 的 assistant 分支把该 id 原样写入出站 input[].id， 而 OpenAI Responses API 只接受服务端签发的 msg_* id—— 换回 400 "Invalid 'input[2].id': 'lc_...'. Expected an ID that begins with 'msg'."。 同样的对话发给 Anthropic / Google 均正常，唯独 OpenAI 崩溃。

框架自铸元数据泄漏到 wire 协议（F9 第2例） 与 #39100 跨 provider 镜像（Anthropic system / OpenAI assistant） ARK 实机离线复现 ✅（无需 API key）

影响范围

langchain-openai 1.4.1 · Responses API + v1 content_blocks 构造合成 AIMessage 的所有用户

框架现状

⚠️ open（2026-07-28 报告）· 无人认领 · 关联 #39100（同族已修复）

ARK 方案

✅ OutputValidator 出站 payload 契约 + InputGuard internal 字段标记

根因定位（P2 Probe）

缺陷是「无形状校验的 id 透传」——出站边界把「有 id」当成了「id 合法」：

  1. create_text_block() 对无 id 的块自动铸造 lc_<uuid4>——v1 内容块把 id 设计为一等公民；
  2. _construct_responses_api_input() 的 assistant 分支读取 msg_id = block.get("id")，只要 store is not False 就写入 new_item["id"] = msg_id——没有任何前缀/形状检查；
  3. 该 id 的设计意图是回传服务端签发的 msg_* item id（stored-replay 场景合法且必要），但框架自铸的 lc_* id 走同一条路径无差别透传；
  4. 对比：human/system 消息块的 id 在同一函数中已被丢弃（用户实测「system 和 human 的 id 已被 pop」），唯独 assistant 分支缺这道清洗——与 #39100（Anthropic 唯独 system 分支缺清洗）构成精确镜像。
# langchain_openai/chat_models/base.py · _construct_responses_api_input() elif msg["role"] == "assistant": ... msg_id = block.get("id") # ← lc_ 或 msg_ 一视同仁 ... else: new_item: dict = {"type": "message", "content": [new_block], "role": "assistant"} if store is not False: new_item["id"] = msg_id # ← 无形状校验，lc_ id 直达 wire input_.append(new_item)

ARK 离线确定性复现（无需 API key）： 通过 ChatOpenAI._get_request_payload() 直接检视出站 payload—— 默认 store=None 时 assistant item 携带 "id": "lc_..."（必 400）； store=False 时 id 被整体省略（合法）； 服务端 msg_* id 正常透传（合法）。三态对照锁死根因。 脚本：scripts/repros/repro_39113_responses_assistant_lc_id_leak.py

💥

后果分析

  • 官方推荐路径先崩：「用 create_* 工厂方法获得校验与标准化」是 v1 迁移指引的核心卖点，越守规矩的用户越先触雷（与 #39047、#39100 同一叙事）；
  • 跨 provider 不可移植：同一份合成历史 Anthropic / Google 正常、OpenAI 400——「provider 无关抽象」承诺在出站边界破产；
  • 合成历史是高频场景：对话压缩/摘要、few-shot 注入、多 Agent 转录回放全部依赖手工构造 AIMessage，此路径覆盖面远大于表面；
  • F9 族复发确认系统性：同一根因（自铸 id 无出站清洗）三个月内在两个 provider 适配器的两个不同角色分支各爆一次，证明「N 适配器 × M 角色分支」的人工纪律必然遗漏。
💊

ARK 处方（P3 Prescribe）

层组件机制
上游修复建议 _construct_responses_api_input() assistant 分支写 id 前加形状校验：仅 msg_id.startswith("msg_")（或非 lc_ 前缀）时保留，否则省略——与 store=False 路径行为对齐
ARK 防线 1 OutputValidator 对每个 provider 声明 wire schema 白名单（OpenAI Responses：input[].id 必须 ^msg_），发送前对账，违规即拦截+告警
ARK 防线 2 InputGuard 框架自铸字段（lc_ 前缀）统一打 internal 标记，任何 internal 字段出现在出站 payload 即契约违规——单点强制取代 N×M 人工纪律
ARK 防线 3 OTel 留痕 ark.validation.fail 事件记录被拦截字段与来源块，替代「400 后从堆栈反推」的排障路径
